## 1. 项目定位与已确认决策

项目从现有微博管理器演进为个人使用的多数据源集成平台。统一前端展示和操作体验，同时保留成熟系统的运行边界，为白酒、记账、证券行情和信息跟踪等能力提供扩展位置。

| 领域 | 已确认方向 |
| --- | --- |
| 前端 | Vue 3 + TypeScript + Vite；目前只有白酒页，统一 SPA 是后续目标 |
| 统一入口 | Nginx 已提供白酒静态资源和 Go 代理；接入微博尚未实施 |
| 微博服务 | 现有 Python 后端完整保留，不重写、不接入新数据库公共层 |
| 新业务后端 | Go，优先轻量、简单、资源可控的实现 |
| 新业务组织 | 单个服务内部按业务模块划分，模块内可以有多个数据源适配器 |
| 数据存储 | 各业务模块使用独立 SQLite 文件，共享新后端内部的数据库基础代码 |
| 仓库 | 继续使用当前仓库，前端、新后端和现有微博系统作为独立子项目 |
| 部署 | 同一服务器、多个容器；开发测试与生产隔离，验证后切换入口 |

选择 Go 是基于当前的新业务以网络采集、结构化数据处理和 API 为主，并重视运行资源与部署简单度。它不意味着所有未来分析任务都必须用 Go，也不意味着可以不经测试就承诺低内存或特定容量。

## 2. 系统边界

```text
Browser :5050                 Browser :5052/liquor
      |                               |
weibospider                    market-entry
Python + original page         Nginx + Vue assets
      |                               |
Existing data.db               platform :5051 (internal)
                                      |
                               liquor.db (separate volume)
```

- 当前两个网页入口独立，没有统一导航。后续目标是在一个 Vue 应用内按模块访问两套后端。
- Nginx 是静态文件服务器和请求转发入口，不执行业务聚合、计算公式或数据库查询。
- Go 后端不成为微博 API 的第二层代理；未来接入微博时由 Nginx 适配原服务路径，当前尚无此映射。
- 微博与 Go 是两个独立服务。白酒、记账等新模块初期不是各自独立的微服务。
- 以后某个模块确有独立扩容、特殊依赖或故障隔离需求时，可以另行拆服务；不提前引入服务发现、消息总线等设施。

当前路径与未来映射的区别：

| 入口与路径 | 去向 |
| --- | --- |
| 5050 的 `/`、`/api/*` | 原微博页面与 API |
| 5052 的 `/`、`/liquor`、静态资源 | Vue 单品行情页 |
| 5052 的 `/api/platform/*` | 保留原路径转发至 Go，仅允许 GET/HEAD；POST 同步不对公网开放 |
| 未来统一入口的 `/api/weibo/*` | 计划映射为原 `/api/*`，当前未实现 |

API 错误响应不能被 SPA 的页面回退规则转换成 HTML 成功响应。图片、上传、PDF 下载、请求方法和查询参数都属于代理验收范围。

## 3. 微博系统保持不变

保留的是整套既有后端，不只是 Scrapy 爬虫文件：

- 微博与评论抓取、增量同步、限速、Cookie 保活和定时调度。
- 当前同属这套后端的雪球能力。
- 数据存储、搜索、回收站、笔记、注解和操作日志。
- 配置管理、图片代理、上传和 PDF 导出。
- 现有 Python 依赖、数据库结构与数据访问方式。

未来微博 Vue 迁移通过已有 API 重建这些能力的展示和交互，不把原有 HTML 页面嵌入作为默认的最终方案。当前旧静态页面仍是正式微博入口，不因白酒新界面出现而删除。业务代码和数据保留不等于容器永不重建：本次共同发布曾重建微博容器。

新前端中的微博 API 客户端负责适配已有字段和响应形态。不能为了统一新旧接口格式，要求微博后端改路由、返回值或数据库表。

微博抓取状态继续采用现有约 3 秒一次的轮询，不向 Waitress 添加 SSE 长连接。新前端需控制轮询数量、请求重叠和日志渲染规模，离开相关页面时清理不再需要的订阅或计时器。

后端不改并不意味着前端迁移无风险。搜索高亮、注解偏移、图片 URL、分页、写操作和下载行为仍需通过新界面与既有 API 的集成测试。

## 4. 前端现状与统一前端目标

当前已实现只读白酒单品页：按酒名/规格搜索、最新价和来源涨跌额、区间首尾价差、7/30/90/365 天历史趋势及明细。金额按人民币分换算；图表异步加载，取消过期请求，不补齐缺失报价。同步状态仅在页面加载和手动刷新时读取，刷新不触发采集。

统一前端迁移仍需按以下方向实施，不代表当前已有导航、路由或微博客户端：

- 建立模块级导航，微博管理与白酒行情是同级入口；未来按实际启用的模块增加记账、证券等入口。
- 微博现有的列表、雪球、笔记、搜索等属于微博模块内部导航，不与平台级业务模块混在同一层。
- 通用布局、导航、反馈提示和 API 请求基础能力可以共享；微博抓取配置、记账表单和行情筛选属于各自模块。
- 使用前端路由实现应用内切换，支持直接访问、刷新和浏览器前进后退。
- 页面按模块组织并按需加载，避免将所有历史数据、图表和业务状态长期驻留内存。
- 模块分别处理加载、空数据、过期数据和失败状态，一个后端暂时不可用时不让整个页面失效。
- 同时验证桌面与移动端。白酒已采用浅色看板和 ECharts；其他模块导航与布局在对应界面设计时确认。

Go 新 API 当前由后端指南、类型定义与测试约定，前端使用手写 TypeScript 类型及 `fetch`；尚未提供 OpenAPI 生成流程。未来可评估生成客户端，微博原 API 单独适配，不要求它新增 OpenAPI 支持。

## 5. Go 后端组织

新后端以 Go 标准库 `net/http` 和 `database/sql` 为基础，按具体需要补充 SQLite 驱动等少量成熟依赖。首期不以大型框架、通用 ORM 或自研插件引擎作为前提。

职责关系如下；这是边界划分，不要求每个简单功能机械拆出多层文件和接口：

```text
HTTP handlers
      |
Module business logic
      |
Module data access
      |
Shared database infrastructure
      |
Module SQLite file
```

公共基础设施只承载真正通用的能力，例如配置、数据库生命周期、HTTP 超时、任务并发控制和诊断日志。业务模型、计算公式、数据清洗规则和业务查询留在模块内部。

### 5.1 模块不等于数据源

| 类型 | 示例 | 职责 |
| --- | --- | --- |
| 业务模块 | 白酒行情、家庭记账、证券行情 | 管理业务模型、API、规则和自己的数据库 |
| 数据源适配器 | 酒价内参、未来的其他酒价或证券供应商 | 请求外部数据、解析、校验并转换为模块可处理的输入 |
| 公共基础设施 | 数据库、任务执行、配置和日志 | 提供不依赖具体业务的运行能力 |

例如，白酒模块接入第二个报价来源时，增加适配器和来源标识，而不是再建一套白酒服务。记账不是一种抓取数据源，不应被塞进统一的采集器数据模型。

### 5.2 插件式扩展的含义

- 初期采用编译进应用的内部 Go 包，通过显式注册和配置启用模块。
- 模块提供自己的路由、数据迁移和任务定义；初始化只影响该模块拥有的资源。
- 新增模块尽量不修改其他模块的业务实现，必要的注册、导航和发布清单可以更新。
- 不实现运行时上传代码、Go 动态插件、第三方插件市场或不可信脚本执行。
- 同一进程里的模块边界是代码组织约定，不是安全沙箱；不可信插件若出现，需要另行设计进程和权限隔离。

## 6. SQLite 存储与公共层

### 6.1 每模块独立文件

SQLite 是应用内嵌数据库引擎，没有一个供所有模块连接的独立 SQLite 服务实例。一个 Go 进程可以通过驱动打开多个文件，不需要为每个数据库文件创建容器或常驻服务。

逻辑归属示意如下，文件名用于表达模块边界，不要求移动或重命名现有微博库：

| 所有者 | 数据文件 | 内容 |
| --- | --- | --- |
| 现有微博服务 | 原位置的 `data.db` | 现有微博、雪球及相关配置和数据 |
| 白酒模块 | `liquor.db` | 酒品、数据来源、日频价格及采集状态 |
| 记账模块，未来增加 | `ledger.db` | 账户、交易、现金流和相关业务记录 |
| 证券行情模块，未来增加 | `market.db` | 证券标识、行情及来源信息 |

新 Go 服务不挂载微博数据库，也不直接查询其内部表。新模块之间只访问自己拥有的表，不借“公共数据库层”取得所有业务库的任意访问能力。

独立文件可以分开管理迁移、写锁和备份，但仍共享服务器磁盘、内存和 I/O，不是资源完全隔离。

### 6.2 公共层与模块层分工

| 能力 | 公共层负责 | 模块负责 |
| --- | --- | --- |
| 连接 | 文件映射、连接生命周期、连接数限制 | 声明需要的数据库和配置 |
| SQLite 配置 | 外键、WAL、锁等待等配置机制 | 根据业务确定持久性、吞吐和超时要求 |
| 事务 | 提交、回滚和错误处理机制 | 确定哪些业务操作必须一起成功 |
| 表结构升级 | 执行迁移、记录版本、防止并发迁移 | 自己的表、索引和升级脚本 |
| 查询与写入 | 使用成熟驱动，不自建万能 CRUD 框架 | SQL、数据映射、去重和业务校验 |
| 备份与诊断 | 一致性备份机制、完整性检查、锁等待和大小指标 | 保留周期、恢复验收和敏感数据要求 |

公共层是 Go 后端内部共享代码，不是额外数据库微服务。现有微博的 `TweetDB` 不接入此层，也不因公共层升级而迁移。

连接配置需根据最终驱动正确应用到实际连接，例如外键和锁等待设置不能只对连接池中的偶然一条连接生效。每个库的连接数、缓存和写入并发有明确上限，不无限创建连接或持有长事务。

SQLite 仍是每文件同一时刻一个写者。WAL 改善读写并发，但不取消写锁。迁移在开放相关模块写入前执行；失败必须明确阻止该模块使用不匹配的结构，不能静默忽略。

### 6.3 事务与跨模块访问

- 按业务一致性边界分库，不按页面或菜单分库。
- 记账的账户、流水和转账应在同一库内完成必要的原子更新，不把一次资金变动拆到不同文件。
- 证券市场报价可以单独存储，用于估值时保留时间和来源口径，不要求它与每笔账务同时提交。
- 同一服务内通过模块接口协作，不必为了模块化绕一圈 HTTP；跨服务才通过 API 通信。
- 不把 `ATTACH` 跨库 SQL 作为模块日常依赖方式。WAL 模式下不能假定多个文件的写入具有跨库原子提交保证。
- 未来只读分析确有跨库需求时，单独评估应用层聚合、只读查询或分析副本，而不是直接开放跨模块写入。

### 6.4 持久化与备份

数据库位于宿主机本地磁盘的持久化目录，数据库和 WAL/SHM 文件处于同一可写目录。备份采用 SQLite 在线备份等一致性机制，不能仅复制运行中的主 `.db` 文件。

不同库分别备份不代表它们具有同一个全局事务时点。恢复说明需记录库版本、应用版本和备份时间，跨模块报表不能据此假定全局强一致快照。

## 7. 采集与后台任务

新 Go 服务初期运行一个 API 进程，内部以有界后台执行方式承载轻量任务，不为白酒日频采集固定增加常驻任务容器。微博继续使用自己的调度器，不接受新平台的重复调度。

- HTTP 请求不能无限等待采集完成；长任务通过任务标识或可查询的运行状态反馈进度。
- 外部请求有超时、取消和有限重试，不无限创建 goroutine，不在数据库事务中执行慢网络请求。
- 同一模块同类同步任务避免重叠。重复采集通过业务唯一键或同步游标保持幂等，不假设任务只会执行一次。
- 模块保存必要的采集状态，重启后能识别中断并安全补采，不能只依赖进程内计时器和“正在运行”布尔值。
- 手动执行与定时执行共用业务路径，统一控制并发和错误处理。
- 日期、采集时刻和调度时区分别明确，不能把抓取时间当成来源报价日期。
- 任务失败不清空已有可用数据，前端展示最后成功时间及错误或过期状态。

以后若出现大批量导入、高频行情或 CPU 密集计算，再根据测量结果拆独立执行进程或服务。不同进程共享某一模块数据库时，必须明确唯一调度者和写入协调方式。

## 8. 首个新模块：白酒行情

第一项新增业务是采集新浪财经“酒价内参”，由 Go 适配器访问来源接口，校验后写入本地 `liquor.db`，前端通过本平台 API 读取，不直接依赖浏览器访问第三方接口。

已在前期调研中实际访问的入口：

- [酒价内参页面](https://finance.sina.cn/app/2025_baijiu_list.shtml)
- [当日列表接口](https://business.cj.sina.cn/api/liquor_price/list)
- [飞天茅台详情样例](https://business.cj.sina.cn/api/liquor_price/detail/1)

前期样本和 2026-09-05 生产验收均观察到 11 个酒品、每品包含当日在内共 31 条记录，合计 341 条报价。这不是来源对品种数、历史范围或接口稳定性的承诺，不能假定没有频控或可以永久获取更早历史。

价格口径按来源公开说明标记为终端零售成交加权均价，不与其他来源的批发参考价混成同一个指标。来源方法论不等于本平台独立核验过原始成交数据。

已保留产品及来源标识、规格、报价日期、整数人民币分价格、单位、价格口径及采集时间。当前唯一键为 `(source, product_id, price_date)`，允许同日来源修正，拒绝旧快照和北京时间未来报价；第二个来源不能覆盖第一个来源的数据。

首期已形成价格、涨跌、历史趋势和采集状态闭环。历史补采仅限来源实际提供且允许访问的范围，长期历史通过持续采集积累。开启自动同步后，每天北京时间 09:00、21:00 各抓取一次；启动不补采，失败或来源未更新时不额外重试，错过执行时间则等待下一个固定时刻。具体边界见 [同步规则](../../backend/README.md#同步规则)。

## 9. 记账与财务计算扩展

Go 可以承担复利、持有期与年化收益率、组合加权收益率、TWR、IRR/XIRR 等计算。记账是后续模块，不在本轮搭建空实现，也不为这些公式引入一个独立计算服务。

- 金额使用最小货币单位整数或明确精度的十进制数，不使用普通二进制浮点直接累计账目。
- 份额、净值和汇率有独立精度要求，不能统一截断为两位小数。
- API 必须明确金额与高精度数值的序列化形式，防止 Go 整数或十进制数经 JavaScript `number` 丢失精度。
- 舍入时机、日数约定、收益区间、分红和费用是否计入、权重定义等属于业务规则，必须明确。
- IRR/XIRR 等数值求解需要收敛条件、误差容限和无解、多解处理，不能失败后返回看似有效的零收益。
- 保留交易、现金流、日期、费用及所需历史估值，不能只靠当前余额推导全部收益指标。

计算代码与数据库访问分离，作为记账或投资领域的可测试函数，不放入数据库公共层。用固定案例和边界测试验证，计算结果说明使用的区间与口径。未来确有大规模统计或研究需求，再考虑按需引入其他工具，不改变现有服务边界。

## 10. 同仓库组织与依赖隔离

当前目录如下。前端仍是精简的单页面组织，没有预建 `src/app`、`src/modules`、`src/shared` 或 `deploy/platform`；后续业务增加时再按实际需要拆分。

```text
WeiboSpider/
  weibospider/                  Existing Python application, unchanged
  frontend/
    package.json / package-lock.json
    src/                        App.vue, TrendChart.vue, market.ts, tests
    Dockerfile
    nginx.conf.template         Liquor read-only entry
  backend/
    go.mod
    go.sum
    cmd/server/                 Go service entry
    internal/
      database/                 Shared SQLite infrastructure
      modules/
        liquor/                 API, ingestion, data access, migrations
    e2e/                        Actual process tests
    Dockerfile
  docs/
  Dockerfile                    Existing Weibo build
  docker-compose.yml            Shared three-service deployment
  install.sh / update.sh        Shared deployment scripts
  requirements.txt              Existing Python dependencies
```

- 同仓库不意味着同语言、同依赖环境或同镜像；当前选择共同发布，独立发布仍是后续优化项。
- Go 使用 `backend/go.mod` 管理依赖，前端使用自己的依赖与锁文件，不修改原 Python 依赖来容纳新项目。
- 新 Go 模块位于同一个 Go 子项目内，不因为每个业务模块独立就各建一份 `go.mod`。
- 公共代码仅在新 Go 后端内部复用，不建设跨 Python/Go 的数据库 SDK 或共享内部模型。
- 前后端接口契约可以配套修改和测试，发布时仍需记录各应用的对应版本。

根 `Dockerfile` 仍使用 `COPY . .`，根 `.dockerignore` 已排除 `backend`、`frontend`、`.github`、私有配置、数据和开发产物；Go 和前端使用各自目录及白名单构建上下文。不要仅依赖 `.gitignore` 判断镜像中是否包含私有文件。push `master` 仍触发三个服务的共同构建与部署，不是按路径独立发布。

新分支与独立工作目录用于开发，新测试 Compose 项目用于运行验证，不在生产检出目录切换分支。正式合并前单独确认发布配置调整，微博业务实现仍保持不动。

## 11. 部署、资源与安全

当前生产已是三个容器，由根 Compose 统一管理。白酒上线前已使用独立目录、网络、回环端口和临时卷进行容器验证，未建立完整微博测试副本。未来微博前端迁移仍需隔离的副本及凭据，不能直接对生产写接口运行测试，见 [部署方案](2026-09-05-multi-source-deployment.md)。

- Vue 构建产物由 Nginx 提供，生产不运行 Vite；当前 Go、Vue 和镜像均在服务器构建，未来可迁入 CI 以降低同机资源峰值。
- SQLite 文件数量不增加数据库服务数量，但连接、缓存、WAL 和磁盘占用仍需分别管理。
- 资源采样只能说明有条件起步。选择 Go 后仍需测试抓取、PDF 导出和新任务的组合峰值，不把语言优势当成容量保证。
- 测试副本使用独立数据和凭据，默认关闭真实调度与外部写入，不能调用生产写接口进行验收。
- 新平台上线后继续需要微博后端。撤下旧页面入口不等于停止仍被依赖的微博服务。
- 身份验证和访问控制必须覆盖统一入口与后端直连路径；处理家庭财务前具备 HTTPS 或受控 VPN 访问等适当保护。
- 按服务挂载需要的数据目录，入口不接触业务数据库；配置、Cookie、数据库和备份不进入 Git 或镜像。
- 缓存、请求体、分页、图表点数、后台任务和日志都有容量边界，不因平台化而无限增长。

## 12. 验证与实施顺序

白酒已先行独立上线，不以完成微博 Vue 迁移为本次验收前提。下列长期顺序中第 1、3 项已有白酒闭环验证，第 2、4 项中的微博迁移和组合负载尚未执行；不把未来清单当作已通过的测试：

1. 准备独立分支与运行环境，建立新前端、Nginx、Go 服务的基础连通和测试隔离。
2. 验证新前端通过代理读取既有微博 API，确定适配边界；写操作仅在测试副本验收。
3. 打通白酒模块的数据采集、独立库、API 和页面，验证公共数据库层与模块注册方式。
4. 完成微博前端功能迁移及完整回归，再进行组合负载、恢复和切换验证。
5. 根据实际需求增加记账、证券等模块，不要求未来模块提前完成才能上线首期平台。

各阶段按实际交付范围验证，至少覆盖：

- Go 业务规则、数据源解析、事务回滚、幂等写入、迁移和备份恢复；数据库测试使用真实临时 SQLite 文件验证驱动行为。
- 后台任务的超时、取消、重试、重叠执行和重启恢复。
- 记账模块交付时验证财务计算的正常与边界案例，包括亏损、零收益、现金流变动、闰年及求解失败，不作为首期白酒模块的前置条件。
- 新前端对既有微博 API 的契约与端到端回归；现有针对旧 HTML 的静态测试不能替代 Vue 交互测试。
- 模块失败隔离、代理错误与下载行为、桌面和移动端访问，以及生产数据不受测试影响。

本文记录现状与后续方向，不授权新的生产修改、提交或推送。下一项交付仍需明确范围和验证要求。
