# 白酒后端真实进程端到端测试记录

日期：2026-09-05

结论：修复一项真实进程停止时的状态分类问题后，后端 API 用户流程通过。此结论不代表 Vue 页面、Nginx 或 Docker 部署已经可用。

## 测试方式

- 工作树：`.worktrees/go-liquor`，分支 `feat/go-liquor`。
- 环境：macOS arm64，Go 1.26.3。
- 测试从源码构建普通发布参数的 `cmd/server` 二进制，用操作系统子进程启动，不调用 `Application.New`、`Serve` 或内部业务方法完成用户操作。
- 服务通过环境变量配置，使用临时 SQLite 目录和系统分配的回环端口。真实客户端通过 HTTP 发起同步和查询。
- 通过 `SIGTERM`、`SIGKILL` 和重新启动二进制验证退出、恢复及持久化；通过只读数据库连接核对行数和 `PRAGMA quick_check`。
- 正常采集使用真实新浪酒价内参。503、错误响应、挂起和自动启动等场景使用本地可控 HTTP 来源，属于故障注入，不冒充新浪实际故障。
- 所有测试服务退出并回收，临时库清理。没有修改微博代码、调用微博接口、连接生产服务器或触碰生产数据，也没有执行部署。

## 真实来源用户流程

| 操作 | 观测结果 |
| --- | --- |
| 启动实际二进制，使用空数据目录 | `/healthz` 返回 200，状态为 `idle`，最新列表为空，默认不自动采集 |
| `POST /api/platform/liquor/sync`，提交 `{}` | 返回 202 和非空 `run_id`，后台开始采集 |
| 任务未完成时再次触发 | 返回 409，未启动第二份并行任务 |
| 轮询同步状态 | 最终为 `succeeded`；修复后整套复测的首次采集约 16.009 秒 |
| 查询最新价格 | 报价日期 2026-09-05，11 个酒品，来源及价格口径字段正确 |
| 逐一查询 11 个酒品的历史 | 每个返回 31 条记录，日期倒序，最新点与最新价格接口一致 |
| 查询同日起止日期及 `limit=1` | 返回该日唯一报价，日期范围包含两端 |
| 再次同步相同日期 | 新任务 ID，库内仍为 341 条报价，无重复行 |
| 正常停止并以同一数据目录重启 | 退出成功，价格、历史及上次成功任务状态保留 |
| 同库启动第二个服务器进程 | 第二个进程被所有权锁拒绝，原服务仍可用 |
| 数据库检查 | 报价总数 341，`quick_check=ok` |

金额示例：飞天茅台 `price_cents=179600`，即 1796 元/瓶。该数值是测试时的来源报价，不是长期固定预期，也不是本平台独立核验过的成交价格。

普通二进制在第二次同步后的一次 RSS 采样为 **19216 KiB，约 18.8 MiB**。这是本机原生进程的单点采样，不是运行峰值，不包括测试进程，也不能据此保证 Linux/Docker 的占用。

## 故障与访问保护

| 场景 | 修复后结果 |
| --- | --- |
| 上游 HTTP 503 | 状态 `failed`，错误代码 `source_unavailable`，上次成功时间与价格保留 |
| 上游返回不合法的空快照 | 错误代码 `invalid_source_data`，不删除旧数据 |
| 上游一直不响应，任务超时配置为 1 秒 | 错误代码 `timeout`，进程保持可用、旧数据保留 |
| 同步中正常发送 SIGTERM | 进程正常退出，任务标记为 `cancelled`，重启后仍能读取旧数据 |
| 同步中发送 SIGKILL | 再启动后任务标记为 `interrupted` / `process_interrupted`，数据库完整性检查正常 |
| 强制停止恢复后重新同步 | 可成功执行新任务，记录数不重复增加 |
| `LIQUOR_AUTO_SYNC=true`、空库启动 | 不调用 POST 即自动采集并入库；使用可控来源验证 |
| 非法日期、反向日期范围、非法或重复 limit、额外 POST 参数 | 返回 400 JSON 错误 |
| 不存在的产品、错误请求方法、错误 Content-Type | 分别返回 404、405、415 |
| 直接请求 Go 服务的微博路径 | 返回 404，不代为操作微博 |
| 外部监听但未配置令牌 | 进程在监听前拒绝启动 |
| 配置令牌后，缺失或错误令牌 | 返回 401 |
| 正确令牌，包括大小写不同的 Bearer 认证方案名 | 返回 200；检查过程日志未包含令牌值 |
| 跨站写请求、无令牌模式下的 DNS 重绑定 Host | 返回 403 |

上述 4xx 和上游故障注入后的任务失败都是预期行为，不是未修复的应用故障。

## 发现并修复的问题

**问题：真实 SIGTERM 取消被错误标记为上游不可用。**

复现路径：启动实际服务器 -> 发起同步 -> 等到外部 HTTP 请求已开始 -> 发送 SIGTERM -> 重启 -> 查询上次任务。

第一次执行得到 `error_code=source_unavailable`，但过程日志显示 HTTP 请求因 `terminated signal received` 结束。进程退出和数据保留本身正常，错误在任务状态及日志分类。

原因：信号触发的取消可以经 HTTP 客户端返回具体的 `context.Cause`。这个错误未必能用 `errors.Is(err, context.Canceled)` 识别，而原 worker 只检查返回错误，没有检查任务上下文已经取消的事实。原先使用普通 `context.WithCancel` 的进程内测试没有覆盖真实信号路径。

修复：`internal/modules/liquor/worker.go` 同时根据任务上下文状态和返回错误判断取消/超时；正常取消记录为 `cancelled`，使用普通信息日志，不再输出上游失败的 ERROR 日志。

回归保障：新增自定义取消原因单元测试，修复前稳定失败；实际子进程 SIGTERM 测试同样修复前失败、修复后通过。随后重跑包含真实来源的全部进程测试和三轮包级竞态回归。

## 复跑命令

在本工作树的 `backend/` 目录执行：

```bash
make check
make test-e2e
make test-e2e-live
go test -race -shuffle=on -count=3 -timeout=5m ./...
go mod verify
```

- `make test-e2e`：真实服务器子进程 + 可控来源，不联系新浪；真实来源测试明确跳过。
- `make test-e2e-live`：另启用真实新浪来源，两轮完整同步；有网络和来源可用性要求，运行时约几十秒，不用于高频循环。
- 测试文件位于 `e2e/`，使用 `e2e` build tag，默认包级测试不自动执行该流程。
- 子进程按正常发布参数构建，以验证用户真正运行的二进制；测试驱动带 `-race`，另外包级竞态回归覆盖服务实现。

修复后最终结果：4 个进程端到端场景全部通过，整个 E2E 测试包约 35.749 秒；三轮随机顺序包级竞态测试、静态检查和依赖校验通过。
