# 投资账本：Excel 重导、回单与重复记录清理（评审稿）

**状态：已按评审实施。** 在同一个账户选择 Excel，点「导入」。系统一次写完，告诉用户**本次**新增和跳过了哪些行。断线后可以从头再导。过去的回单可以查，不限制有删除依据的账户记录移除。

本稿以 `a3ff165` 的实现为基线。第一期简化导入和回单；已确认的三笔重复记录单独清理；账户资金流 MCP 放在下一期。**本轮沿用现有逐行去重规则**，不自动识别改备注、改日期或不同币种下的疑似同一笔交易。

## 1. 回单到底留什么、去掉什么？

现在口头说的“回单”实际包含几种不同的东西：

| 信息 | 回答什么问题 | 本方案的取舍 |
| --- | --- | --- |
| 本次导入差异 | 这一份文件刚刚新增几行、跳过几行？ | **保留弹窗。** 用本次文件、事务内比对结果和本文件的行号生成，不需要读取历次回单才能展示。 |
| 导入批次清单 | 某一次导入当时写入了哪些编号？ | **去掉对清单的强制依赖。** 旧清单不改写。新导入可以留批次号、时间和数量作来源说明，无需再保存第二份“所有新增账本 ID 清单”并要求这些行永久存在。 |
| 请求回执 | 同一个提交请求是不是已经成功过？ | 保留已有接口的防重复提交能力和旧回执兼容。它是请求级保护，不是普通用户重导文件的前置条件，也不参与收益计算。 |
| 原始导入行 | 这个账户以前从 Excel 导入过什么，各出现过几次？ | **保留。** 这是重导时的比对依据。原始资料描述过去导入的事实；账户记录描述今天仍应计入账本的事实。两者可以不同。 |

**为什么不直接改旧清单？** 假设原文件确有 100 行，当时也成功写入了 100 行。后来发现一行重复，正确结果是“当时导过 100 行、现在只有 99 行有效”，而不是把当年的回单改成“只导过 99 行”。这一差别只影响追溯；资产、净流入和收益率一律按有效账本算。

## 2. 用户怎么导入？

1. 选择目标账户和文件，点「导入」。先解析并校验文件，不写库；币种不符或文件无效时直接提示原因。
2. 后端在同一事务内按该账户**当时已提交**的来源行重新比对。即使两个人同时导入，也不能各拿一份旧预览分别追加。
3. 提交成功后弹出「本次导入差异」，仍分为「新增记录」「跳过的重复记录」。**新增数 + 跳过数 = 本次文件有效行数**；明细里的 Excel 行号指本次文件。提交失败则不显示成功差异。

**断线示例（合成数据）：** 一个已有账户原先导过 97 行，这次送入 100 行。如果上次事务没有提交，重导结果是「新增 3，跳过 97」；如果服务器已提交，只是浏览器没收到响应，重导结果是「新增 0，跳过 100」。两种情况下最终都只入账 100 行。页面只需提示“结果未确认，请在原账户重新导入”，不用锁住页面、强制使用专门的「重试导入」按钮。发请求期间仍应防止重复点击。

**首次导入同时新建账户，是唯一需要额外处理的情况。** 新建前固定目标账户 ID，暂存文件摘要和该 ID，不保存 Excel 内容。断线后按该 ID 和首次导入的文件摘要核实：已经建成就选回原账户，未提交就沿用原 ID。若浏览器已丢失这段关联，请用户从账户列表选择目标或明确新建，不能只凭同名猜测，也不能每次点击都生成另一个账户。创建账户和写入首批记录必须在同一事务内完成。

## 3. 比对及写入：沿用原规则，只换数据依赖

**比对范围是“本账户已接收的原始 Excel 行”**，不是所有账户、手工记账记录或个股流水。现有匹配键使用类型、业务日期、资金流、总资产、备注、明细和规范化后的来源创建时间；文件行号和日期的原始写法不参与。金额按精确值比较，空金额与明确的零不同。按出现次数一对一匹配：历史有两笔完全相同的转入，新文件有三笔，只新增一笔。

| 输入情况 | 本轮结果 |
| --- | --- |
| 完全相同的文件再次导入，或只是行顺序变了 | 已出现的次数全部跳过。 |
| 文件是历史的子集，或中间补了一笔较早的记录 | 不删除文件中没出现的旧账。补录的行按正常规则比对，确实缺少才新增。 |
| 在有知有行改了备注或业务日期 | **仍可能算作新增。** 自动覆盖旧行、模糊匹配和冲突处理面板都已暂缓。 |
| 一笔业务行被明确删除，旧文件仍含原样的行 | 原始来源行仍在，按现有规则跳过。没有新增“永久排除名单”；如果源行的字段又改了，仍适用上一条。 |

**事务边界：** 文件解析、大小与格式校验在事务外。正式写入时，先校验账户与文件摘要，再读取来源行并计算差异；新增账户（如有）、账本行、来源行、审计和必要的请求回执一起提交。只在提交成功后返回数量和坐标。任何一步失败，整批回滚。普通重导是一次新的比对；同一请求键和相同参数的网络重发沿用原回执，同键不同参数拒绝。两者都不能重复入账。

## 4. 存储改动与旧数据兼容

**现状：** `readImportHistory` 会遍历历史批次的 `record_ids`，再把每条原始导入证据和 `account_records` 中的业务行对上。数据库触发器也禁止给仍存在的账户直接删除单条记录。因此，只删一行业务数据会使导入历史校验失败。

**建议改法：**

- 以账户内不可变的 `import_row` 原始证据作为比对来源。新导入不再逐批查验每个历史编号是否还在业务表。若需加速，可为“账户、现有行匹配键、出现次数”建立可重建索引；不改变匹配语义。
- 当前账本列表、账户汇总和收益查询继续读取 `account_records`；「原始导入资料」从来源证据读取。历史导入笔数和当前有效笔数允许不同，界面不可把前者标为当前记录数。
- 原始凭据仍然校验：业务行消失时，能用限定到账户、记录、原版本及原因的删除审计解释；无法解释的缺失仍是数据异常。删除审计只证明一次维护操作，不拿它代替逐行去重。
- 保持现有预览、确认、导入结果、汇总和分页接口兼容。旧客户端依赖的 `batch_id`、新增/跳过数和混合结果的 `added_source_rows` 继续可读；旧请求按原键重放仍返回原结果。每笔来源证据已经记录了来源批次和 Excel 行号，重放可以据此还原，不需反查仍然有效的业务行。
- 升级先在隔离副本校验旧清单与原始证据。迁移仅调整结构、读取路径及受控删除规则；不改写历史回单、不在迁移中自动删除业务数据。已有回执也用于其他写入，不能清空共享回执表。

## 5. 已确认的三笔：单独的数据维护

这次要的是从**当前账户记录中真正移除**：有效列表和“显示已作废”列表都查不到被移除的记录。网页原有的作废接口和持仓流水接口不需要因此改变。准确 ID、保留项、用户确认的金额和收益试算见单独交付的本地核对表。

1. 建立 SQLite 一致性备份并验证可恢复。在副本中核对账户、三组删除/保留 ID、版本、原始批次及币种。确认清理作用于账户资金记录，不动真实的个股买卖、费用或持仓数量。
2. 在**一笔维护事务**内复查前置条件，写删除审计，只移除三条指定业务行。保留项状态或版本变化就整批停止。事务同时推进账户收益数据的变更版本，标记受影响的最早日期；已删除的稳定编号不得分配给新记录。
3. 读回全部有效记录、三条保留项、转入转出合计、期末资产和同一区间收益率。副本中再次导入原文件应新增零笔，下一份有新行的文件应能正常追加。读回不符则停止后续写入，按一致性备份及操作后新增记录评估恢复；不能直接拿旧快照覆盖他人的后续写入。

**维护工具：** [ledger-remove-import-duplicates.py](../../scripts/ledger-remove-import-duplicates.py) 只接受先核准的私有计划。计划指定账户、币种、`expected_revision`、每对 `remove` / `keep` 的 ID、版本与原 payload 的 SHA-256、`reason`，以及删除前后的 `[有效笔数, 转入分, 转出分]`。默认运行整笔事务、验证结果后回滚；`--apply` 必须同时指定一个**不存在的**备份文件，先取得写锁并用另一连接备份、检查 SQLite 完整性和外键，再提交。公开仓库不保存真实计划或备份。迁移 011 不会自行清理账户。

## 6. 验收标准

| 测试 | 通过条件 |
| --- | --- |
| 正常导入及重导 | 合成示例首次新增 3 行，再导新增 0 行；弹窗的数量、分组和本文件行号一致。 |
| 中途失败、提交后丢失响应 | 在写到一半时注入故障，没有半套账本、来源或审计；响应丢失后用普通导入即可恢复，首次新建场景也不重复建账户。 |
| 并发、重复次数和账户隔离 | 相同或重叠文件并发，只新增实际缺少的次数；真实的多笔相同转入不被吞掉，其他账户不受影响。 |
| 规则没有扩张 | 改过备注的行按原规则处理，不自动改写旧账；缺历史行的子集不导致隐式删除。 |
| 删除后仍可导入 | 三条指定业务行不存在，原始导入资料可读；同文件再导新增 0，文件再加一笔则只新增 1。人为破坏一条无删除依据的数据，完整性检查仍能检出。 |
| 旧库及旧客户端 | 既有批次、旧请求回执可读；原键原参数重放保持原结果，普通重导得到本次结果；导入摘要、原始行分页与有效账本各自口径一致。 |
| 收益与回滚 | 清理前后按同一区间、同一口径核对资金加权收益率及 XIRR，结果符合本地核对表；任一版本冲突时三条均不变，备份可恢复。 |
