# 多数据源平台部署方案

日期：2026-09-05

状态：白酒首期已部署并合入 `master`，2026-09-05 验收版本为 `e2c5476`。当前是根 Compose 统一发布三个独立容器，保留微博 5050，新增白酒 5052；不是按模块独立发布，也还不是统一网页入口。

整体职责、同仓库组织、数据库边界和财务计算原则见 [多数据源平台整体架构说明](2026-09-05-multi-source-architecture.md)。实际命令见 [部署运维](../deploy-prep.md)，驱动、API 和表结构见 [Go 指南](../../backend/README.md)，发布过程和公网测试结果见 [生产验收记录](../validation/2026-09-05-liquor-production.md)。

## 1. 目标与边界

- Vue 3 + TypeScript + Vite 已实现白酒单品页；全面重构并在一个应用内展示微博及其他模块是后续目标。
- 保留现有微博服务的实现、API 和数据，包括抓取、调度、Cookie 保活、雪球、搜索、注解、图片代理及 PDF 导出。
- 新业务采用独立 Go 后端，白酒、记账等先作为其内部模块运行，不默认每个模块一个微服务。
- 开发和验证使用独立分支、独立检出目录、独立 Docker Compose 项目、新端口与独立持久化目录，不干扰现有生产环境。
- 本文记录现状与后续方案，不授权新的生产修改、提交或推送；已经执行的发布与测试以验收记录为准。

## 2. 正式运行拓扑

同一台服务器运行多个容器，不在一个容器中嵌套运行其他容器，也不需要新增虚拟机。

```text
Shared root Docker Compose project

Browser :5050                Browser :5052/liquor
      |                              |
weibospider                  market-entry :8080
Python + original page       Nginx + Vue static assets
      |                              |
./data bind mount            platform :5051 (internal)
                                     |
                             platform-data volume
```

| 容器角色 | 职责 | 不承担的职责 |
| --- | --- | --- |
| `market-entry` | 提供 Vue 白酒页，转发 Go 行情只读请求 | 不代理微博，不直接访问数据库 |
| `weibospider` | 继续运行原网页、Python 后端、抓取和调度 | 不接管新模块的数据和任务 |
| `platform` | Go 白酒 API、自动采集和独立 SQLite | 不导入微博内部代码，不直接读写微博数据库 |

- Vue 构建后是静态文件，生产环境不运行 Vite 开发服务器，也不因 Vue 额外常驻一个 Node 服务。
- 前端框架不决定后端语言；新后端基于轻量与资源可控的取舍选定 Go，不要求微博服务更换语言或实现。
- SQLite 是内嵌引擎，模块的多个数据库文件由 Go 服务访问，不需要额外 SQLite 服务或容器。
- 首期不强制增加独立的任务执行容器。后台任务不能长期阻塞请求处理，并需限制并发；重任务出现后再评估独立执行进程或容器。
- 三个容器已经加入同一根 Compose 项目；本次共同发布重建过微博容器，但没有改动其业务代码、依赖或数据布局。“独立运行”不等于“独立发布”。

## 3. 入口与网络

当前两个公网入口并行，统一入口仍是未来工作：

| 外部请求 | 当前处理位置 |
| --- | --- |
| 5050 的 `/`、`/api/*` | 原微博网页与 API |
| 5052 的 `/`、`/liquor` 和静态资源 | Nginx 返回 Vue 单品行情页 |
| 5052 的 `/api/platform/*` | 保留原路径转发给 Go，仅允许 GET/HEAD |
| `/api/weibo/*` | 未实现；未来迁移时再配置为原 `/api/*` |

- 未来微博代理需适配路径前缀，不要求微博服务修改现有路由。
- 当前行情代理的 API 错误不会被 SPA 回退掩盖。未来微博图片、上传、PDF 导出和错误转发还需单独验收，不算本次已交付功能。
- 微博抓取状态继续使用现有的轮询接口，不向 Waitress 引入 SSE 长连接。
- Go 的 5051 仅容器内部开放；旧微博暂保留公网 5050，新 Nginx 使用公网 5052。云安全组和宿主机防火墙均需按实际入口配置。
- 服务令牌由服务器 `.env.platform` 提供，Nginx 在上游请求中注入，不发送给浏览器；这不是用户认证。POST 同步被公开入口拒绝，生产采集由 Go 自动任务执行。
- 新测试入口不得路由到生产微博写接口。前端测试中的删除、注解编辑、修改配置、抓取操作不能影响生产。
- 新测试实例仍需另选不冲突的回环端口、独立网络和存储，不能复用两个生产入口或生产卷。
- 后续统一入口和限制旧端口的变更需单独确认；当前尚未配置 HTTPS 或完整登录，不用于承载敏感财务数据。

## 4. 后续微博迁移的测试隔离

原方案中的完整三容器测试副本尚未建立。本次白酒上线前只在隔离环境验证了 Go 与 Nginx，未复制微博生产库。未来迁移微博前端时需保留生产服务，另建以下测试环境：

```text
Existing production
  Three production containers + their existing storage

Independent test project
  Entry container
  Platform container + test business storage
  Weibo test container + isolated test storage
```

- 新项目使用独立 Compose 项目名、网络、容器名和数据目录，避免与现有 `weibospider` 固定容器名冲突。
- 微博测试副本使用与生产匹配的既有实现，记录代码版本和镜像标识；不能用会漂移的镜像标签替代版本记录。
- 生产库若需作为测试样本，使用 SQLite 在线备份 API 等一致性备份方式，不能直接复制运行中的主 `.db` 文件并忽略 WAL。
- 测试副本启动前清理真实 Cookie、OSS 凭据和其他外部服务配置。Cookie 文件、日志及临时输出也必须与生产隔离。
- 测试初始化时关闭自动调度和 Cookie 保活，并限制真实抓取的外部请求；只有隔离端口、关闭浏览器或隐藏抓取按钮都不够。
- 当前 `create_app()` 会初始化数据库并启动调度。测试启动方式必须验证不会触发真实任务，不能把未核验的环境变量当成已有禁用开关。
- 普通回归使用测试数据和模拟外部响应。真实抓取、上传及 PDF 峰值测试单独安排，避免两套环境同时使用同一账户执行任务。

## 5. 数据与持久化

- 微博继续使用现有持久化目录和数据库，不要求为了新平台更名、搬迁或迁移表结构。
- 新业务使用独立持久化目录，不挂载微博生产数据库给新业务容器。
- 当前微博绑定挂载 `/opt/weibospider/data/`，白酒使用 `platform-data` 命名卷（本次实际名 `weibospider_platform-data`）；Go 容器内库为 `/app/data/liquor.db`，非 root UID 1000。
- 各服务仅挂载自身需要的数据目录。入口容器不挂载业务数据目录。
- SQLite 使用宿主机本地磁盘上的持久化存储，数据库和对应 WAL/SHM 文件保持在同一可写目录，不使用临时容器文件系统保存正式数据。
- 现有微博容器以 UID 1000 运行，其数据目录权限要求不变；新服务的目录权限根据自身运行用户单独配置，不对整个生产目录统一修改所有权。
- 备份包含数据库版本、应用版本和恢复说明。使用一致性备份机制并验证恢复，不能只确认备份文件存在。
- 新业务按模块使用独立 SQLite 文件。连接、事务机制、迁移执行和一致性快照通过 `backend/internal/database` 管理；表结构、业务查询及事务边界属于模块，见 Go 指南。当前没有公开运维备份 CLI 或 HTTP 备份端点。
- 公共数据库层不是额外服务，也不要求既有微博服务接入。各库分别备份不等于获得跨模块的全局事务快照。

## 6. 服务器资源与容量边界

以下保留 2026-09-05 部署前的资源采样；CPU 核数来自此前同机检查，不是此刻的实时状态。数值不是容量承诺，也不是抓取或 PDF 导出时的峰值。

| 项目 | 观测值 |
| --- | --- |
| CPU | 2 vCPU |
| 总内存 | 3660 MiB，约 3.6 GiB |
| 可用内存 `available` | 1248 MiB，约 1.22 GiB |
| 微博容器当时内存 | 54.55 MiB |
| 微博容器当时 CPU | 0.01% |
| 已使用 Swap | 374 MiB |
| 根分区剩余空间 | 11 GB，使用率 82% |

部署前的初步预算保留如下，不能直接作为容器内存上限：

| 新增部分 | 初步预算 |
| --- | --- |
| Nginx 和静态文件服务 | 数十 MiB |
| 少量模块、轻任务的新业务后端 | 沿用选型前约 100 至 300 MiB 的初步预算，Go 实现后重新测量 |
| 未运行抓取的微博测试副本 | 约 50 至 100 MiB |

同日生产公网验收后的一次空闲采样为：微博约 55.8 MiB、Nginx 约 3.4 MiB、Go 约 5.8 MiB，容器重启计数均为 0。它们不能替代长时运行或抓取/PDF/构建叠加时的峰值测试，也不能与不同平台的原生进程 RSS 直接比较。

- 首期微博管理、白酒日频采集和少量个人记账有条件在现有服务器上运行，不要求立即升级。
- 该判断不覆盖全市场高频或逐笔证券数据采集，也不覆盖不限量的历史数据处理。
- 必须测试抓取子进程、Chromium/PDF、新业务任务和并行测试的组合峰值，观察内存、换页、CPU、磁盘 I/O 和接口响应。
- 不把 Swap 当成额外物理内存，也不按微博当前的空闲占用设置过低内存上限。
- 新增服务的资源限制在测试后确定；设置限制不能代替容量验证，内存超限可能导致进程被终止。
- 磁盘预算需覆盖镜像、回滚版本、测试数据副本、数据库 WAL、日志和备份。清理操作需另行确认，不默认执行 Docker prune。
- 同机容器隔离不等于硬件完全隔离，新旧环境仍共享 CPU、内存和磁盘资源。

## 7. 构建与发布

- 当前工作流只监听 push `master`，SSH 到 `/opt/weibospider` 执行 `update.sh`；快进拉取后重新执行新版脚本，初始化缺失的 `.env.platform`，运行根 `docker compose up -d --build`，检查双入口并通知邮件。
- 当前三个镜像都在服务器构建，各自使用独立上下文、Dockerfile 和依赖；尚未实现 CI 预构建分发或按模块独立发布。迁入 CI 可降低小服务器构建峰值，是后续优化而非当前能力。
- 前端、Go 后端和 Python 系统不共用运行环境，但共同部署仍可能重建任一发生镜像或配置变化的容器，不能保证“仅改白酒就绝不重建微博”。
- 根 Dockerfile 仍使用 `COPY . .`，根排除规则已隔离前后端新目录、私有配置、数据、`.github` 和工作树等；新增目录时仍需核验。Go/前端使用白名单构建上下文，数据和服务令牌不进入镜像。
- 发布记录包含前端、微博服务、新业务服务的对应版本和镜像标识，保留可回滚版本。
- 现有 `.github/workflows/deploy.yml` 在 push `master` 时部署到原生产目录。测试分支的发布必须使用独立目标，不能复用原生产路径或误触原更新流程。
- 安装脚本和更新脚本会生成缺失的服务器配置，但部署账户必须有正确的源码及配置权限；运维检查不要打印 `.env.platform` 或完整展开的 Compose 配置。

## 8. 验收与正式切换

白酒首期已上线：真实自动采集、Nginx 只读 API、公网页面、单品切换、日期筛选、明细及移动模拟视口通过。旧微博入口仍可用，没有进行微博前端迁移、生产数据库恢复或高并发/组合负载测试。完整证据和非阻断提示见生产验收记录。

后续统一入口和微博迁移仍需以下验收，不能将未做项目标记为通过：

1. 验证隔离：测试数据、凭据、任务和写接口均不影响生产。
2. 验证新前端通过代理使用微博全部既有能力，包括列表、评论、雪球、搜索、回收站、注解、配置、日志、图片、上传和导出。
3. 验证白酒模块的采集、持久化、重复执行及失败恢复；未实际实现的未来模块不作为此次验收前提。
4. 验证容器重启后的数据和任务行为，以及任一后端失败时前端可显示局部错误、不造成整页崩溃。
5. 验证组合负载和备份恢复，并在切换前记录最终部署版本和回滚路径。
6. 经用户确认后切换入口，新前端接入正式后端；测试数据库不能直接覆盖仍在更新的生产数据库。

保留微博后端是本方案的前提，因此“撤下旧页面入口”不等于“停止微博服务”。优先保留现有正式微博服务，只切换前端入口。原生产入口的公开访问是否保留需结合访问控制单独处理。

如果以后确需把微博服务迁入新的 Compose 项目，应作为独立迁移操作处理：安排停止写入的窗口、准备最终一致性数据、迁入相同已验证实现，并保证同一真实账户只有一个有效抓取调度实例。不能在新平台仍依赖旧容器时直接关闭它。

前端或代理失败时优先回滚入口和对应应用版本。回滚不能直接恢复旧数据库覆盖切换后产生的新数据；涉及数据库结构变更时，需另行制定兼容或恢复方案。

## 9. 安全要求

- 测试入口限制访问，不把携带真实样本的测试系统无保护地开放到公网。
- 家庭财务等敏感模块上线前，必须具备适当的身份验证、访问控制及 HTTPS 或受控 VPN 访问，不能继续按普通公开行情页面处理。
- 保护统一入口的同时，必须处理后端端口的直接访问，避免绕过入口保护。
- 数据库、Cookie、密钥和备份不进入 Git、构建上下文或镜像；新增构建流程需核验排除规则，不能只依赖 `.gitignore`。
- 日志避免记录凭据和完整财务数据，备份访问权限按其敏感程度管理。

## 10. 后续讨论边界

Go、CGO SQLite、迁移、白酒 API、Vue/ECharts 和三服务部署已经落地，具体职责见整体架构说明。后续重点是多品对比、统一导航/微博迁移、完整访问控制、备份恢复与独立发布；不要求原微博服务接入新的公共数据库代码，也不提前搭建未使用的业务模块。
